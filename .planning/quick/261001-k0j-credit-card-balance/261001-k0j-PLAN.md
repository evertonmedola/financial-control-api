<objective>
Treat a credit-card account's balance like any other account's balance (user-chosen "option B"): negative balance = open debt, and the consolidated net balance is the plain sum of all account balances.

Purpose: today `ReportsService.getNetBalance` special-cases `AccountType.CARTAO_CREDITO` and SUBTRACTS the card balance as if it were a stored positive "amount owed". But `TransactionsService`/`TransfersService`/`AccountsService.adjustBalance` already apply signed deltas with no card branching, so a card at 0.00 charged R$ 100 becomes -100.00 and the net balance goes UP by 100 (wrong). The Swagger/DTO text also still promises the old positive-debt convention. This supersedes Phase 2 decision D-01 and Phase 6's per-type netting decision, per the user's explicit request (not a research choice).

Output: uniform `getNetBalance`; unit + e2e tests covering the new behavior (expense on card, payment, net); Swagger/DTO/comment wording fixed; PROJECT.md key-decision row updated.

Source coverage (quick task: no CONTEXT.md/RESEARCH.md; sources are the user request + ROADMAP/REQUIREMENTS refs):
- User bullet 1 (getNetBalance uniform sum) -> Task 1
- User bullet 2 (remove "amount owed"/"valor devido" from Swagger + DTOs, describe negative = open debt) -> Task 3 (plus test titles in Tasks 1-2)
- User bullet 3 (card 0.00 + R$100 -> -100.00 and net -100.00; payment reduces debt; e2e) -> Tasks 1 and 2
- User bullet 4 (check reports and dev data) -> findings in `<context>` + dev-data note below; no further code change required
- REQ ACCT-03 / REP-02 -> refined by Tasks 1 and 3 (both stay satisfied: card is still a liability, now expressed by sign)
No item is deferred or unplanned.

Dev-data note FOR THE USER (not a task; the repo has NO seed script, NO seed SQL, NO data INSERTs in migrations, and docker-compose has no init SQL, so there is nothing in the repo to migrate and no already-applied migration is touched): any credit-card row in the user's LOCAL database that was created under the old convention with a positive balance (e.g. 500.00 meaning "I owe 500") will now read as a positive asset. Cards that also received expenses were moved by the old code in the opposite direction of their own convention, so the stored number is no longer trustworthy. Simplest fix, run by hand on the local DB only: set the card balance to the NEGATIVE of the real outstanding debt, e.g. UPDATE accounts SET balance = -<real outstanding> WHERE id = '<card id>'; or delete the card and recreate it with a negative initial balance. The AWS stack is documented as throwaway-data-only, so no production data migration is planned.
