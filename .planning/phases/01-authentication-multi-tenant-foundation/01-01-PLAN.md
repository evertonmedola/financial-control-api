## Phase Goal

> The ROADMAP.md Goal line for Phase 1 is prose, not pre-formatted as a user story ("Users can create an account, log in securely, and trust that their data is isolated from every other user..."). No `/gsd mvp-phase 1` reformatting pass has run. Rather than block planning or invent new scope, this framing is a direct, faithful restatement of that same Goal line's own actors/capability/outcome into the template — no content added beyond what ROADMAP.md already states.

**As a** new user, **I want to** sign up, log in, and access my own data through the API, **so that** I can trust my financial data is isolated from every other user from day one.

## Acceptance Criteria
- [ ] A visitor can register with email+password; the password is hashed with argon2id, never stored or returned as plaintext
- [ ] A registered user can log in and receive a JWT that authenticates subsequent requests, with no server-side session lookup
- [ ] Requests to a protected endpoint without a valid JWT are rejected
- [ ] A user's JWT only ever grants access to that user's own data
</user_story>

<objective>
Stand up the entire NestJS project from nothing (Walking Skeleton) and wire the first real end-to-end auth path: a visitor registers, logs in, and uses the resulting JWT to reach a protected route that proves per-user data isolation. This is Phase 1's tracer bullet — production-quality, not a prototype — and the architectural backbone (module layout, `userId`-scoping pattern via `@CurrentUser()`, response shape) every later phase (Accounts, Categories, Transactions, Budgets, Reports) builds on without alteration.

Purpose: Prove the full stack (NestJS -> TypeORM -> Postgres -> Passport/JWT) works end-to-end before layering refresh-token rotation, transport hardening, and rate limiting on top of it (Plans 02-05).
Output: A running NestJS app, a Dockerized local Postgres, a `User` entity + migration, and three working endpoints (`POST /auth/register`, `POST /auth/login`, `GET /auth/me`) fully covered by `test/auth.e2e-spec.ts`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> `POST /auth/register` / `POST /auth/login` | Untrusted credentials cross here; must be validated, hashed, and never echoed back |
| Client -> `GET /auth/me` (Bearer token) | Untrusted bearer token crosses here; must be cryptographically verified before any DB lookup runs |
| `AuthService` -> `users` table | Only place plaintext-adjacent data (the hash) is persisted; only place ownership scoping is enforced |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Information Disclosure | `AuthService.validateUser()` (login) | high | mitigate | Generic error message (D-05) + dummy-hash timing mitigation (Pattern 2): both branches call `argon2.verify()` so a scripted attacker cannot distinguish "email exists" from "email doesn't exist" by response time |
| T-01-02 | Tampering / Information Disclosure | `GET /auth/me` + `@CurrentUser()` | critical | mitigate | `userId` is sourced exclusively from `JwtStrategy.validate(payload.sub)` -> `request.user.userId`; the controller never reads a client-supplied `userId` from query/body for scoping — the pattern every later module (Phase 2+) reuses |
| T-01-03 | Spoofing | JWT signature verification (`JwtStrategy`) | high | mitigate | `@nestjs/jwt` + `passport-jwt` pin the verification algorithm and handle signature checks out of the box — never hand-rolled; `secretOrKey` sourced from a Zod-validated env var, never hardcoded |
| T-01-04 | Information Disclosure | `AuthService.register()` / any logging | medium | mitigate | Plaintext password is passed in-memory to `argon2.hash()` only; no `console.log`/`Logger` call anywhere in `src/auth` receives `req.body.password` or the raw password variable (prohibition P1) |
| T-01-05 | Information Disclosure | JWT payload (`AuthService.login()`) | medium | mitigate | Access token payload carries only `sub`/`iat`/`exp` — no email/PII field (prohibition P2) |
| T-01-SC | Tampering | npm installs (`@nestjs/jwt`, `@nestjs/passport`) | high | mitigate | package-legitimacy gate + blocking-human checkpoint (Task 0) before either package is installed |
</threat_model>
