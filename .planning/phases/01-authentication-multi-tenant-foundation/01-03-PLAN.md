From `01-RESEARCH.md` Pattern 3 (the exact rotation/reuse-detection logic to implement):
```typescript
async refresh(rawRefreshToken: string) {
  const tokenHash = this.hashToken(rawRefreshToken);
  const stored = await this.refreshTokenRepo.findOne({ where: { tokenHash } });
  if (!stored) throw new UnauthorizedException();
  if (stored.revokedAt) {
    // Reuse of an already-rotated token — treat as compromise.
    await this.refreshTokenRepo.update({ userId: stored.userId, revokedAt: IsNull() }, { revokedAt: new Date() });
    throw new UnauthorizedException();
  }
  if (stored.expiresAt < new Date()) throw new UnauthorizedException();
  await this.refreshTokenRepo.update(stored.id, { revokedAt: new Date() });
  return this.issueTokenPair(stored.userId); // new access + new refresh, new RefreshToken row
}
private hashToken(raw: string): string {
  return crypto.createHash('sha256').update(raw).digest('hex');
}
```

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client -> `POST /auth/refresh` / `POST /auth/logout` | Untrusted refresh token crosses here; must be hash-looked-up, never trusted as an identity claim on its own |
| `AuthService` -> `refresh_tokens` table | The only place a stolen/replayed token's blast radius is contained (family revocation) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01-08 | Elevation of Privilege | `AuthService.refresh()` | high | mitigate | Rotation + reuse detection (Pattern 3): replaying an already-rotated token revokes the entire token family for that userId, forcing full re-login |
| T-01-09 | Information Disclosure | `refresh_tokens` storage | medium | mitigate | Only a SHA-256 hash of the refresh token is persisted, never the raw value — a DB read never yields a usable token (prohibition P1 of this plan) |
