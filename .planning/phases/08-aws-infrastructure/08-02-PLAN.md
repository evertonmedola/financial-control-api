Deliver the tracer slice of the whole phase: ONE request travelling Internet -> ALB -> private Fargate task -> private RDS, with runtime-injected Secrets Manager credentials, applied for real and proven with a real HTTP call. Because every layer this phase touches sits on that single path, the tracer is the complete thin stack: VPC with public/private subnets in two AZs and one NAT (D-04, D-05), three SG-to-SG-linked security groups, RDS PostgreSQL 16 with an RDS-managed master secret (D-07, D-08), the CLI-created JWT secret referenced through a data source (D-09), least-privilege execution role, ALB on HTTP:80 (D-06), and the ECS Fargate service running the existing ECR image by immutable tag. Purpose: Prove the architecture end to end while it is one commit old. The riskiest unknowns from research — NAT egress to ECR/Secrets Manager/Logs, RDS-managed secret json keys, RDS forcing TLS against an app with no `ssl` option, image CPU architecture — all surface in this single apply, on the plan's best early context.
Output: `infra/network.tf`, `infra/rds.tf`, `infra/secrets.tf`, `infra/alb.tf`, `infra/ecs.tf` applied to AWS; a live `GET /health` = 200 through the ALB.

    Per the project process, this is the architecture discussion before execution, with the reason for each AWS service (Cloud Practitioner study notes):

    - VPC + 2 public / 2 private subnets in 2 AZs (D-04): network isolation; the ALB and the RDS subnet group both require at least two AZs, which also demonstrates high availability across AZs.
    - Internet gateway + ONE NAT gateway in AZ a (D-05): the ALB lives in public subnets; tasks and RDS live in private subnets with no public IP, and the NAT gives tasks outbound-only internet to pull the image from ECR, read Secrets Manager and write CloudWatch Logs. A single NAT is a deliberate cost/availability trade-off.
    - Security groups, SG-to-SG (D-05): stateful virtual firewalls; RDS trusts only the task SG, tasks trust only the ALB SG (least privilege at the network layer).
    - Application Load Balancer, HTTP:80 (D-06): the only internet-facing component; layer-7 routing plus health checks so only healthy tasks receive traffic. HTTPS is deferred, so until it exists no real financial data may be sent to this endpoint.
    - ECS Fargate (2 tasks): serverless container runtime — you manage the task definition, AWS manages the servers (shared responsibility). Image comes from the private ECR repository by immutable tag.
    - RDS PostgreSQL 16, db.t4g.micro, single-AZ (D-07): managed database (AWS patches and backs up; you own the data and the schema). Multi-AZ is deferred.
    - Secrets Manager (D-08, D-09): RDS creates and owns the DB password secret; the JWT secret was created by CLI in Plan 08-01; ECS injects both at container start, so neither is in the image, the environment block or Terraform state.
    - IAM roles: the execution role is what ECS itself uses to pull the image, write logs and fetch the two secrets; the task role (empty) is what the app would use for its own AWS calls.
    - CloudWatch Logs and S3 (state, from Plan 08-01): observability and Terraform's durable state.

    Cost while the stack is up: CONTEXT.md estimates the NAT gateway alone at about US$32/month (us-east-1 list price); sa-east-1 list prices are typically higher [ASSUMED — check the AWS Pricing Calculator], and the ALB, RDS db.t4g.micro, 2 Fargate tasks, 20 GB gp3 and two Secrets Manager secrets add to that — on the order of a few US dollars per day [ASSUMED]. Everything except the S3 state bucket, the JWT secret and the ECR repository disappears with `terraform destroy`; you are expected to run it whenever the stack is idle (infra/README.md documents it in Plan 08-04).

    Reversibility: the apply itself is fully reversible with `terraform destroy` (RDS is configured with skip_final_snapshot and no deletion protection precisely for that); the only real cost of "approve" is hourly billing until you destroy.
