  <context>
    Per the project process, this is the architecture discussion before execution, with the reason for each AWS concept (Cloud Practitioner study notes):

    - IAM OIDC identity provider: tells AWS to trust identity tokens signed by GitHub's issuer (`token.actions.githubusercontent.com`). GitHub is not an AWS service; this is federation. Free.
    - STS `AssumeRoleWithWebIdentity`: swaps a GitHub-signed, short-lived token for temporary AWS credentials (about one hour). Nothing long-lived is stored in GitHub, which is the whole point of INFRA-03 (Cloud Practitioner: IAM, temporary security credentials, federated access, least privilege).
    - The deploy role has two policies with different jobs: the TRUST policy says WHO may assume it (only workflow runs on `main` of this repository, audience `sts.amazonaws.com`, using GitHub's immutable subject that embeds numeric owner and repository ids so a renamed or re-created repo of the same name cannot impersonate this one) and the PERMISSIONS policy says WHAT it may do once assumed (push to one ECR repo, register task definitions, update one service, run one migration task; nothing else).
    - `iam:PassRole` restricted to the two ECS roles with `iam:PassedToService = ecs-tasks.amazonaws.com`: CI may hand only those roles to ECS. Known trade-off: registering a task definition plus PassRole is the classic escalation path; it is bounded by the trust policy (main only) and deferred hardening (branch protection, pinned actions).
    - ECR lifecycle policy: keeps the 10 newest images so storage does not grow with every commit (managed registry, pay-as-you-go). The bootstrap image tag `c0ebba2` will eventually be pruned, which the runbook will explain.
    - ECS: every deploy registers a new task-definition REVISION (immutable, versioned), then the service does a rolling update; the deployment circuit breaker (already enabled in Phase 8) rolls back a failing rollout (managed service, high availability). Migrations run as a one-off Fargate task inside the VPC because the private RDS is unreachable from GitHub's runners.

    Cost: the OIDC provider, role, policies and ECR lifecycle rule are free. The apply ALSO recreates the whole Phase 8 stack, which was destroyed for cost control at the end of Phase 8: NAT gateway, ALB, RDS db.t4g.micro, 2 Fargate tasks, 20 GB gp3, two Secrets Manager secrets - hourly billing, on the order of a few US dollars per day [ASSUMED, sa-east-1 pricing is higher than the CONTEXT.md estimate], for about 15-20 minutes of apply time. The database will be EMPTY; the first pipeline run's Migrate step creates the schema, so no manual migration is needed. Everything is reversible with `terraform destroy` (now also removing the role and provider; a later apply recreates them with the same names and ARNs, so the GitHub variable stays valid).

    Reversibility: reversible. The only cost of `approve-apply` is hourly billing until you destroy; Plan 09-05 ends with a keep-or-destroy decision.
