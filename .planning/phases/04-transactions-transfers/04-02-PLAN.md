<objective>
Expand the Transactions vertical slice from create-only to full CRUD: a user can list, view, update the description/date of, and delete only their own income/expense transactions, with `amount`/`accountId`/`categoryId` permanently locked after creation (D-04) and every deletion atomically reversing the exact balance effect it originally applied (D-06) — guarded against the double-reversal race a naive soft-delete would allow.

Output: `UpdateTransactionDto`, the remaining four CRUD service methods and controller routes, a dedicated Transactions cross-tenant/IDOR test suite mirroring `test/categories-cross-tenant.e2e-spec.ts`.
</objective>

    Add to `TransactionsService` in `src/transactions/transactions.service.ts`: `findAll(userId: string): Promise<Transaction[]>` via `this.transactionsRepository.find({where: {userId, deletedAt: IsNull()}, order: {date: 'DESC', createdAt: 'DESC'}})` — D-10's `date` DESC primary sort with `createdAt` DESC as an explicit, deterministic tiebreak when two rows share the same `date` (no analog in Accounts' `createdAt ASC`; this is a new, fully-specified ordering rule, not left implicit). Note this list includes ALL types (income/expense/transfer) per D-03 — do not filter by `type` here.

    `findOne(userId: string, id: string): Promise<Transaction>` via `findOne({where: {id, userId, deletedAt: IsNull(), type: In([TransactionType.INCOME, TransactionType.EXPENSE])}})`, throwing `new NotFoundException()` when not found. The `type: In([...])` filter is the key architectural decision this task makes: single-record view/update/delete on `/transactions/:id` is scoped to income/expense rows ONLY — a transfer's id looked up through this method returns 404, exactly as if it didn't exist for this endpoint, forcing all transfer mutation through the dedicated `/transfers/:id` routes (04-03). This is necessary, not just stylistic: `remove()`'s single-account reversal logic below would be actively wrong (it reads `transaction.accountId`, which is `null` on a transfer row) if a transfer ever reached it — excluding transfers at the query level closes that gap structurally rather than relying on a runtime null-check.

    `update(userId: string, id: string, dto: UpdateTransactionDto): Promise<Transaction>`: calls `this.findOne(userId, id)` first (ownership + type-scope check before mutation), then `Object.assign(transaction, dto)` and `.save()` — `dto` can never carry `amount`/`accountId`/`categoryId` since the DTO layer excludes them.

    `remove(userId: string, id: string): Promise<void>` — D-06's atomic locked reversal: open `const queryRunner = this.dataSource.createQueryRunner(); await queryRunner.connect(); await queryRunner.startTransaction();`, then in `try`: `const transaction = await queryRunner.manager.findOne(Transaction, {where: {id, userId, deletedAt: IsNull(), type: In([TransactionType.INCOME, TransactionType.EXPENSE])}, lock: {mode: 'pessimistic_write'}});` — locking the transaction row itself (not just the account) is what makes a second concurrent DELETE on the same id resolve to 404 instead of double-reversing: the second call's `findOne` (same WHERE, same lock) blocks until the first transaction commits, then re-reads with `deleted_at IS NULL` no longer true, finding nothing. `if (!transaction) throw new NotFoundException();`. Compute the exact inverse of what `create()` applied: `const reversalDelta = transaction.type === TransactionType.INCOME ? negateDecimalString(transaction.amount) : transaction.amount;` (income was created as `+amount`, so reversal is `-amount`; expense was created as `-amount`, so reversal is `+amount` — import `negateDecimalString` from `../common/decimal.util`). Call `await this.accountsService.adjustBalance(queryRunner.manager, userId, transaction.accountId!, reversalDelta);`, then `transaction.deletedAt = new Date(); await queryRunner.manager.save(transaction);`, then `await queryRunner.commitTransaction();`. In `catch`: rollback + rethrow. In `finally`: release.

    Add to `TransactionsController` in `src/transactions/transactions.controller.ts`: `@Get() async findAll(@CurrentUser() userId: string): Promise<TransactionResponseDto[]>`. `@Get(':id') async findOne(@CurrentUser() userId: string, @Param('id') id: string): Promise<TransactionResponseDto>`. `@Patch(':id') async update(@CurrentUser() userId: string, @Param('id') id: string, @Body() dto: UpdateTransactionDto): Promise<TransactionResponseDto>`. `@Delete(':id') async remove(@CurrentUser() userId: string, @Param('id') id: string): Promise<Record<string, never>>` calling `transactionsService.remove` then returning `{}` (mirrors `AccountsController.remove()`'s established 200-plus-empty-envelope convention).
